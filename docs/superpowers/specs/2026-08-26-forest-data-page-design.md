## คำถามตั้งต้น

> "อยากได้หน้าแยกสำหรับเก็บข้อมูลป่าไม้ที่หน้าแผนที่ดำเนินการมา — เรื่องป่าชุมชนกับหมุดพิกัด

คำว่า "ยังไม่ใช่" ถูกต้อง และเหตุผลอยู่ในไฟล์ ไม่ใช่ในความรู้สึก — แกะแผนที่ป่าไม้ตัวจริงแล้ว

## 2. สามข้อที่ทำให้ของเดิม "ยังไม่ใช่"

### 2.1 ป่าชุมชนขาดไปครึ่ง

| | หมู่ 7 | หมู่ 9 | หมู่ 10 | หมู่ 11 |
|---|---|---|---|---|
| ไร่ (ทะเบียนในไฟล์) | 463 | 707 | 50 | 1,941 |
| อยู่ในพอร์ทัลวันนี้ | ❌ | ❌ | ✅ | ✅ |

`public/Shapefiles ป่าชุมชน.zip` ที่ `import:forest` ใช้ มีแค่หมู่ 10 กับ 11 — หมู่ 7 (463 ไร่)
และหมู่ 9 (707 ไร่) ไม่เคยเข้าระบบ

**ข่าวดี:** `computeArea` ที่ทำไว้รอบที่แล้วเชื่อถือได้ ระบบคำนวณหมู่ 11 ได้ **1,941.21 ไร่**
ทะเบียนในไฟล์เขียน 1,941 ไร่ 0 งาน 81.59 วา = **1,941.20 ไร่** — ต่างกัน 0.005%

### 2.2 "หมุดพิกัดป่าชุมชน" 176 จุด ไม่ใช่ชั้นข้อมูล

เป็นหมุด GPS ที่ใช้รังวัดลากขอบเขต (polygon หมู่ 10 มี 59 จุดยอด = จำนวนหมุด 59 จุดพอดี)
ขอบเขตที่ได้อยู่ในชั้นป่าชุมชนเรียบร้อยแล้ว แผนที่ป่าไม้ตัวจริงจึงไม่มีชั้นนี้ และหมู่ 7 กับ 9
ก็ไม่มีหมุดให้ตั้งแต่แรก → **ลบเลเยอร์ `community-forest-point` ทิ้ง**

### 2.3 หมุดที่มีจริงคือ "ฝาย" — และเป็นข้อมูลสองชุดปนกัน

`fid` แบ่งตัวเองอยู่แล้ว: **1–41 กับ 42–54** ตัดขาดกันพอดี ไม่มีจุดไหนคาบเกี่ยว

| | `fid` 1–41 | `fid` 42–54 |
|---|---|---|
| จำนวน | 41 | 13 |
| ชื่อฝาย | ❌ (`Name` = `Photo(1).jpg`) | ✅ `ฝายม่อนหินขาว ม.7`, `ฝายสภาเด็ก`, `ฝายโรงหล่อพระ` … |
| รูป | อ้างถึง 41 รูป | ❌ |
| `Altitude` | ✅ 335–356 ม. | ❌ |
| วันที่ | `2025-06-18` / `2025-06-20` เท่านั้น | 13 วันต่างกัน ครอบปี 2564–2568 |
| `cause` | ❌ | `ภัยแล้ง ไม่มีน้ำ` ทุกแถว |

คือชุดแรกเป็น **การเดินสำรวจถ่ายรูปสองวันในมิถุนายน 2568** ชุดหลังเป็น **ทะเบียนฝายที่สร้างจริง
ย้อนหลัง 5 ปี** และคอลัมน์ชื่อ `loss` ที่จริงเก็บ *ชื่อฝาย* ไม่ใช่ความเสียหาย

สองเรื่องพ่วง:

- **รูป 41 รูปไม่มีอยู่บนเว็บ** — ยิงทดสอบทุกทางได้ 404 `Path` ชี้ไป
  `D:/Qgis/ป่าไม้/ฝาย\Photo(1).jpg` บนเครื่องคนทำ QGIS วันนี้คลิกหมุดบนแผนที่ป่าไม้จึงเห็นรูปแตก
- **`fid` 54 ซ้ำสองแถว** — QGIS แจกเลขพลาด แต่พอแยกเป็นสองชั้นแล้วคีย์สะอาดทั้งคู่

## 3. การตัดสินใจที่ตกลงแล้ว

1. **ยกมาครบทั้ง 6 ชั้น ไม่ clip** — รวมป่าสงวน/ป่าถาวรที่เป็นข้อมูลกรมป่าไม้ระดับจังหวัด
2. **แยกทั้งหลังบ้านและหน้าสาธารณะ** — `/admin/forest` + `/forest`
3. **ลบ `community-forest-point`** (176 หมุดรังวัด)
4. **แยกชั้นฝายเป็นสองชั้น** → รวมเป็น **7 ชั้น**
5. **แยกโดเมน `forestLayers`** ไม่ใช่เพิ่มฟิลด์ `group` บน `MapLayer`
6. **`forest` เป็นสิทธิ์แยก** และเจ้าหน้าที่ **สร้างชั้นใหม่เองได้**

| `map-stats.ts` | 96 | ไม่ | import ตรง ๆ |

**แยกจริงสี่อย่าง:** collection · URL · หน้าเว็บ · สิทธิ์
**ใช้ร่วมหนึ่งอย่าง:** ตรรกะบริสุทธิ์ ~980 บรรทัด — ป่าไม้จึงได้ด่านตรวจครบ 14 รหัส ระบบร่าง/

และไม่มีใครรู้จนกว่าจะมีคนบ่น

### เหตุผลสามข้อที่ต้องบันทึกไว้

**`FR_NAME` ซ้ำ** — `ป่าแม่ยวมฝั่งซ้าย` มีสองแถว จึงต้องใช้ `NRF_CODE` เป็นคีย์ ถ้าใช้ชื่อจะติดด่าน
`duplicate-key` ทันที (เหตุผลเดียวกับที่ถนนต้องใช้คีย์ประกอบ)

**`objectid` ทิ้งเพราะเคยเจอมาแล้ว** — ชั้นอาคารไม่ตั้งคีย์เพราะ ArcGIS แจก `OBJECTID` ใหม่ทุกรอบ
export ป่าถาวรมีปัญหาเดียวกัน `per_id` (`pf00330`) เป็นรหัสจริงที่คงที่

**`computeArea` เปิดเฉพาะป่าชุมชน** — ป่าสงวน/ป่าถาวร/คทช. มีเนื้อที่ทางการติดมาในไฟล์แล้ว
ถ้าเปิดจะได้ตัวเลขที่สามที่ไม่ตรงกับอีกสอง แล้วคนเอาไปอ้างผิดบนพอร์ทัลราชการ ป่าชุมชนเป็นชั้นเดียว
ที่ไฟล์ไม่มีเนื้อที่ทางการมาให้

### ป้ายกำกับที่ต้องเขียนให้ตรง

- `area_rai` (ป่าชุมชน) = **"พื้นที่โดยประมาณ (ไร่)"** — คำนวณจากรูปทรง
- `rai_gazette` (ป่าสงวน) = **"เนื้อที่ตามกฎกระทรวง"**
- `rai_rfd` = **"เนื้อที่ตาม GIS กรมป่าไม้"**

สามอย่างนี้ไม่ใช่สิ่งเดียวกัน

## 6. `coordinatePrecision` — พิกัดพกความละเอียดเกินจริงมา 14 ตำแหน่ง

ทุกชั้นเก็บพิกัดถึง 14 ตำแหน่งทศนิยม = ระดับต่ำกว่านาโนเมตร เป็นขยะทศนิยมลอยตัวจากการแปลง
พิกัดใน QGIS ไม่ใช่ความแม่นยำจริง

| ชั้น | จุดยอด | ตอนนี้ | ปัด 6 ตำแหน่ง | ลด |
|---|---|---|---|---|
| ป่าสงวน | 172,710 | 6.34 MB | 3.60 MB | −43% |
| ป่าถาวร | 115,265 | 4.20 MB | 2.40 MB | −43% |
| แหล่งน้ำ | 7,278 | 0.34 MB | 0.22 MB | −35% |
| คทช. | 6,042 | 0.22 MB | 0.13 MB | −41% |
| **รวม** | | **11.1 MB** | **6.4 MB** | |

ที่ละติจูด 18.7°N ทศนิยมตำแหน่งที่ 6 = **11 เซนติเมตร** ละเอียดกว่าเครื่องรังวัดที่เก็บข้อมูลชุดนี้
หลายเท่า

**อยู่ที่ pipeline ไม่ใช่ที่สคริปต์** — เพิ่มฟิลด์ `coordinatePrecision?: number` บน **`MapLayer`**
(ไม่ใช่ `ForestLayer` เพราะ pipeline ใช้ร่วมกันทั้งสองโดเมน) คู่ขนานกับ
`computeArea` ด้วยเหตุผลเดียวกัน: ถ้าสคริปต์เป็นคนปัด วันที่เจ้าหน้าที่ export จาก QGIS มาลากวางเอง
ไฟล์จะกลับไปบวม 6.34 MB เงียบ ๆ โดยไม่มีด่านไหนเตือน

แทรกใน pipeline:

```
parseMapFile → [ปัดพิกัด] → [เติม area] → computeStats → sha256 → runChecks → computeDiff
```

ต้องปัด **ก่อน** `computeStats` และ `sha256OfFeatureCollection` เหมือน `withArea` ไม่งั้นอัปไฟล์เดิม
ซ้ำแล้ว sha ไม่ตรง ตรรกะ "ข้ามถ้าเหมือนเดิม" ของสคริปต์กับด่าน `identical` พังทั้งชุด

ชั้นแผนที่เดิมทั้งสี่ไม่ตั้งค่านี้ (`undefined` = ไม่ปัด) พฤติกรรมจึงไม่เปลี่ยน
ฟอร์มสร้างชั้นใหม่ตั้งค่าเริ่มต้นเป็น 6

## 7. `iso-date.ts` — วันที่ 3 รูปแบบในคอลัมน์เดียว

```
2025-06-18   → 2025-06-18   ISO ค.ศ. อยู่แล้ว
18-มิ.ย.-68  → 2025-06-18   พ.ศ. 2 หลัก + เดือนย่อไทย
๑๒-มิ.ย.-๖๖ → 2023-06-12   เลขไทย + พ.ศ. 2 หลัก
๒๐-ก.ย.-๖๔  → 2021-09-20
```

**แปลงไม่ได้ = โยน error หยุดการนำเข้า** ไม่ปล่อยค่าเดิมผ่านไป — ปีที่อ่านผิดบนทะเบียนฝาย
คือความเสียหายที่ไม่มีใครสังเกตจนสายเกินไป

และปฏิเสธปีที่อยู่นอกช่วง ค.ศ. 1900–2100 ด้วย — ที่พบบ่อยคือ ISO ที่ปีเป็น พ.ศ.
(`2568-06-18`) ซึ่ง Excel ภาษาไทยผลิตออกมาเองโดยคนกรอกไม่รู้ตัว ถ้าปล่อยผ่านจะได้ปีที่คลาด
ไป 543 ปีโดยไม่มีอะไรเตือน

เป็นฟังก์ชันบริสุทธิ์ เทสต์ครบทั้งสามรูปแบบได้ตรง ๆ (ไฟล์นี้ถูกอ้างถึงในแผนรอบ 3A ของสาธารณสุข
ด้วย — รอบนี้เป็นผู้เรียกใช้จริงตัวแรก)

## 9. สร้างชั้นใหม่เองได้ — `/admin/forest/new`

ปิดหนี้ที่สเปกรอบป่าชุมชนตั้งใจผัดไว้ (*"ทำ A ก่อน แล้วค่อย B"*) วันนี้ `upsertLayer()` ถูกเรียกจาก
สคริปต์ที่เดียว เจ้าหน้าที่สร้างชั้นเองไม่ได้เลย

```
1  ลากไฟล์วาง            .geojson · .js (qgis2web) · .zip (shapefile)
2  เบราว์เซอร์แกะก่อนอัป   → รู้รูปทรง จำนวน feature รายชื่อฟิลด์ ค่าตัวอย่าง
3  ฟอร์มถามเฉพาะสิ่งที่ไฟล์บอกเองไม่ได้
4  สร้าง → ชั้นใหม่ + เวอร์ชัน 1 สถานะร่าง ต้องกดเผยแพร่อีกที
```

| ช่อง | ระบบเติมให้ | คนกรอก |
|---|---|---|
| `geometryType` | อ่านจากไฟล์ แล้ว **ล็อก** | — |
| `id` | slug จากชื่อ + ตรวจซ้ำ | แก้ได้ |
| `title` / `description` | — | ✅ |
| `keyFields` | แสดง **"ฟิลด์นี้ไม่ซ้ำ 41/41 แถว"** ข้างทุกตัวเลือก | ✅ เลือก |
| `computeArea` | ติ๊กได้เฉพาะรูปปิด | ✅ |
| `coordinatePrecision` | ค่าเริ่มต้น 6 · **รับ 4–9 เท่านั้น** | แก้ได้ |
| `publicFields` | **ปิดทุกฟิลด์เป็นค่าเริ่มต้น** | ✅ ติ๊กเปิดทีละอัน |

**`geometryType` ล็อกไว้** เพราะมันคือสาเหตุที่ไฟล์ป่าชุมชน 4 แปลงอัปทับของเดิมไม่ได้
(`Polygon` vs `MultiPolygon`) ให้คนเลือกเองเมื่อไหร่ ก็ตั้งผิดแล้วติดด่านทุกครั้งเมื่อนั้น

**`coordinatePrecision` ต้องมีขอบเขต** — ตอนนี้เป็นค่าที่ dev ตั้งในไฟล์ ไม่มีใครพิมพ์ผิดได้
แต่เมื่อขึ้นเป็นช่องบนฟอร์ม `0` จะกลายเป็นค่าที่กรอกได้ ซึ่งปัดพิกัดเหลือองศาเต็ม = คลาด
**111 กิโลเมตร** และผ่านทุกด่านตรวจไปได้สบาย ๆ เพราะยังอยู่ในกรอบประเทศไทย จำกัดที่ 4–9
(4 = 11 เมตร หยาบสุดที่ยังใช้งานได้ · 9 = ละเอียดกว่าข้อมูลต้นทางทุกชุด)

**การบอก distinct ข้าง `keyFields`** มาจากบทเรียนจริง: `full_id` ของถนนซ้ำ 138 แถว, `point_n`
ของหมุดป่าชุมชนซ้ำ 59 ค่าข้ามหมู่ — ทั้งสองครั้งรู้ตอนอัปแล้วติดด่าน ถ้าโชว์ตัวเลขตอนเลือก
จะรู้ตั้งแต่ก่อนสร้าง

**ไม่มีทางลัด** — `POST /api/admin/forest/layers` เรียก `ingestMapFile()` ตัวเดียวกับที่ลากไฟล์วางเรียก

### ต้องมีปุ่มลบชั้นด้วย

สร้างได้แต่ลบไม่ได้คือกับดัก — สร้างผิดครั้งเดียวแล้วค้างถาวร ลบชั้นต้องลบเวอร์ชันทั้งหมด **และ
ไฟล์บน Cloudinary** ตามไปด้วย ไม่งั้นไฟล์กำพร้าจะกองสะสมโดยไม่มีอะไรอ้างถึง (หลักเดียวกับที่
`versions.ts` ลบไฟล์ทิ้งทันทีเมื่อไม่ผ่านด่าน) **สองอย่างนี้ต้องขึ้นพร้อมกัน**

### `forest-registry.ts` ไม่ใช่แหล่งความจริง

เมื่อเจ้าหน้าที่สร้างชั้นเองได้ ฐานข้อมูลคือความจริง ไฟล์ registry เหลือหน้าที่เดียวคือเป็นเมล็ดพันธุ์
ของสคริปต์นำเข้าครั้งแรก — ถ้าปล่อยให้เป็นแหล่งความจริง วันที่เจ้าหน้าที่เพิ่มชั้นเองแล้วมีคนรัน
สคริปต์ซ้ำ ชั้นนั้นจะหายหรือถูกเขียนทับ

## 10. รูปฝาย — เก็บนอกไฟล์ GeoJSON

**ไม่เขียน URL รูปลงในไฟล์** ด้วยเหตุผลเดียวกับ `computeArea` และ `coordinatePrecision`:
วันที่เจ้าหน้าที่ export จาก QGIS มาลากวางทับ ฟิลด์นั้นหายไปทั้งคอลัมน์ ด่าน `field-removed`
เตือนแค่ระดับ warning กดเผยแพร่ผ่านได้ แล้วรูปทั้ง 41 รูปหลุดจากหน้าเว็บเงียบ ๆ

```
forestPhotos   { layerId, featureKey, publicId, url, bytes, uploadedAt, uploadedBy }
```

ตอนกดเผยแพร่ ระบบคำนวณคีย์ของแต่ละ feature (ฟังก์ชันเดียวกับที่ `runChecks` และ `computeDiff` ใช้)
แล้วเติม `photo_url` ลงในไฟล์สาธารณะ — อัปไฟล์ใหม่กี่รอบรูปก็อยู่ครบ เพราะรูปไม่เคยอยู่ในไฟล์แต่แรก

**คีย์ของชั้นนี้คือชื่อไฟล์รูปพอดี** ลาก 41 ไฟล์วางทีเดียว ระบบจับคู่ `Photo(17).jpg` เข้ากับหมุด
ที่คีย์ `Photo(17).jpg` ตรงตัว ไม่มีการเดา แล้วรายงานว่าไฟล์ไหนจับคู่ไม่ได้

**`photo_url` เติมหลังกรองฟิลด์ และเปิดด้วยสวิตช์ `publishPhotos` ที่ค่าเริ่มต้นเป็นปิด** —
หลักเดียวกับ `publicFields` ที่ปิดทุกฟิลด์โดยค่าเริ่มต้น รูปถ่ายภาคสนามอาจติดคนหรือติดบ้านคนมา
โดยไม่มีใครตั้งใจ หน้าตั้งค่าจึงเรียงรูปทั้ง 41 ใบให้ดูเป็นแผงก่อน แล้วค่อยกดเปิด

เมื่อต้องการ

**สไตล์และป้ายชื่อ** เติมใน [`map-style.ts`](../../../src/lib/map-style.ts) สามที่:

  ป่าสงวนแยกตาม `province`
- `FIELD_LABELS` — ป้ายไทยในป๊อปอัป

## 13. ที่ยังค้าง — ต้องถามเจ้าของข้อมูล

**คทช. มีเนื้อที่สองชุดในแถวเดียวกัน**

| ชุด | ค่า | ตรงกับ |
|---|---|---|
| `Rai` / `Ngan` / `wa` | 5,935 ไร่ 1 งาน 36 วา | `Shape_Area` = 9,496,546 ตร.ม. |
| `R` / `Ng` / `Twa` / `RA` | 5,746 ไร่ 1 งาน 58 วา | `A` = 9,194,232 ตร.ม. |

ต่างกัน **189 ไร่** น่าจะเป็นวงรอบทั้งหมด vs พื้นที่จัดสรรจริง แต่เดาแทนไม่ได้ — รอบนี้เก็บชุดใหญ่
ไว้ชุดเดียว และ **ต้องถามเจ้าของข้อมูลว่าชุดไหนคืออะไรก่อนเปิดสาธารณะ**

**รูป 41 รูป** — เจ้าของข้อมูลรับปากจะหาต้นฉบับจากเครื่องที่ทำ QGIS มาให้ รอบ 4 เริ่มไม่ได้จนกว่า
จะได้ไฟล์

**การเผยแพร่ไม่ได้เป็น atomic** — พบตอนรีวิว Task 3 ไม่ใช่ของใหม่ที่รอบนี้ทำขึ้น
`buildPublishPatch` เป็นฟังก์ชันบริสุทธิ์ที่คำนวณอย่างเดียว ส่วน `publish.ts` เขียนสามครั้ง
เรียงกันโดยไม่มี transaction (ทั้ง repo ไม่มี `startSession` เลย) ถ้าโปรเซสตายหลังตั้ง
เวอร์ชันใหม่เป็น `published` แต่ก่อนตั้งตัวเก่าเป็น `superseded` จะเหลือ `published`
สองตัวพร้อมกัน

**ผลกระทบจริงเบากว่าที่ฟัง** เพราะ `/api/map/layers/index.ts` หยิบด้วย `.find()` บนลิสต์ที่
เรียงใหม่สุดก่อนอยู่แล้ว จึงได้ตัวใหม่ซึ่งเป็นตัวที่ถูกต้อง ส่วน `getPublishedVersion()`
ใช้ `findOne` ที่ไม่เรียง จึงคืนตัวไหนก็ได้ — โดเมนป่าไม้สืบทอดพฤติกรรมนี้มาทั้งดุ้นเพราะ
ใช้ `layer-store` ตัวเดียวกัน

**ทางแก้ที่น่าจะถูกกว่า transaction** — partial unique index บน `{ layerId }` ที่กรอง
เฉพาะ `status: 'published'` จะบังคับข้อสมมตินี้ที่ชั้นฐานข้อมูลตรง ๆ การเขียนครั้งที่สอง
ที่จะทำให้มีสองตัวจะล้มเองทันที ไม่ต้องพึ่ง transaction ไม่ต้องแก้ `publish.ts` และ
`ensureIndexes()` ใน `layer-store.ts` ก็เป็นที่ที่จะสร้าง index ตัวนี้อยู่แล้ว

ยังไม่ทำในรอบนี้เพราะเป็นพฤติกรรมเดิมที่การแยกโดเมนไม่ได้แตะ และการเพิ่ม unique index
ลงบนข้อมูลที่ผลิตอยู่จริงต้องตรวจก่อนว่าวันนี้ไม่มีเลเยอร์ไหนมี `published` ซ้ำอยู่แล้ว
ไม่งั้น `createIndexes` จะล้มเงียบ ๆ ทุกครั้ง (มันถูกห่อด้วย try/catch) ควรเป็นงานของ
ตัวเองที่มีขั้นตรวจข้อมูลก่อน — จับคู่ไปกับงานยุบตัวช่วย `mongo()` ในรอบ 1B ซึ่งเป็น
การทำให้ข้อกำหนดเป็นเรื่องเชิงโครงสร้างเหมือนกัน

JSDoc ของ `getPublishedVersion` เขียนความจริงข้อนี้ไว้แล้ว เพื่อไม่ให้คนถัดไปสร้างของ
ทับบนสัญญาที่ไม่มีอยู่

**`แผนที่ป่าชุมชนหมู่ที่ 102_modified.tif`** — raster 46 MB ในซิปเดิม ยังอยู่นอกขอบเขตเหมือนรอบที่แล้ว
